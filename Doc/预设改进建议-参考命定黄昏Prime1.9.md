## 3. 优先建议：动作依赖与结算事实

### P1-1：区分可尝试、已完成和等待前提

**现状：** 真实难度已有动作与期望结果拆分、逐项校验，但后续行为依赖前一动作结果的表达还不够明确。

**建议：** 在短链 Step 1 用简短状态区分：可发起、不可发起、待前提。可发起不等于已成功；只能继续执行前提已满足的后续动作，不必为每个日常动作增加冗长表格。

例如“买丹→服丹→突破”：交易未完成不能服丹；服丹结算后的修为未达到阈值不能开始突破。某一步失败不应抹掉此前已经成立的步骤，也不应自动兑现后续步骤。

**涉及：** `🎚️真实难度(三选一)`、短链中英文 Step 1/3。需要核对另外两档难度是否应共享同一事实边界。

**验收：** 用缺钱购买、缺材料制作、修为不足突破三种输入，检查未满足的后续步骤不会成为事实。

### P1-2：前置计划不得冒充本轮结算

**现状：** 短链在正文和面板之前就要求列“本轮真实发生”的变化，但部分结果此时尚未成立。

**建议：** Step 4 区分“已确认／待结算／不变”；前置检查只列变动对象及条件，具体值等待对应面板。主 API 变量只写最终成立的事实，额外 API 根据实际正文与面板更新，不把前置计划当证据。

**涉及：** 短链 Step 4、两种变量模式条目、世界书变量更新规则。

**验收：** 计划成功但实际失败的生产不能增加成品；计划购买但交易中断不能扣钱或入库；已扣资源不能再次扣除。

### P1-3：明确规则“可用”和业务“触发”的区别

**现状：** COT 通过 `路由隐藏规则` 过滤候选清单；未被隐藏并不意味着本轮一定要执行该规则。

**建议：** 明确两层判断：规则确实在本轮提供，且剧情已经达到触发条件。买卖中的一句“以后突破”不能触发突破面板。保留路由失败时的既有降级逻辑，不简单将所有判断改为“必须在命中列表中”。

世界推进仍由卡内专用脚本核对请求和时间区间；仅在预设中写“明确要求时触发”不能替代现有固定路由和防重复结算。

**涉及：** COT、卡内世界推进桥、预设与世界书中的触发摘要。路由插件仍保持通用。

**验收：** 分别测试普通过滤、固定路由、路由失败降级、额外 API 跳过/复用，不能只测一次普通发送。

## 4. 叙事与玩家控制

### P2-1：对白比例服从情境与玩家权限

当前启用的对白要求为 50%。建议将其改为适用场景下的目标比例，而非每轮硬约束；独处、炼丹、战斗、昏迷等场景允许缩减。

禁止抢话时，不得为了凑对白而替玩家回答、点头、默许、跟随或接受交易。允许转述既有输入，也不意味着允许创造新的决定。

参考预设在这方面写得更具体：对白条件与玩家代写权限直接联动，而不是把两个互相冲突的开关交给模型自行协调。

### P2-2：场景节点数服从本轮边界

本次保留短链原有的“2—4 个连续场景节点”，但建议后续允许：普通叙事按需规划，战斗按现有回合限制，生产按当前阶段，等待玩家选择时停在选择之前。

字数与节点数不能促使模型额外旅行、发起新战斗、替玩家交易或结束尚未完成的流程。

### P2-3：保留仙侠语言，减少句式负担

可以借鉴“舒展叙事”的具体方法：相关动作衔接清楚，名称不随意缩写，篇幅靠取舍细节而不是省助词、堆四字短句或不断解释动作来调整。

叙事可以使用自然数量描述；面板、价格、骰子、变量必须保留准确值。去套话不等于去掉“识海、丹田、灵根”等世界内术语。

现有“每句对白先模拟两个版本”的选项目前关闭，建议继续关闭；不要为改善对白额外复制整轮台词。

## 5. 格式和脚本协作

### P2-4：用统一输出说明约束既有标签

建议将现有输出格式明确为：规划闭合 → 一个 `<now_plot>` → 内部正文及其面板 → 按开关输出后置模块。应以当前正则、正文美化和 MVU 读取方式确定准确嵌套，不照搬命定的 `<tp>` 位置或外层包装。

命定的 XML Schema 只是写在提示词中的格式约定，不是 API 强制校验器。更实际的增强是检查重复根标签、缺失闭合、变量模式与输出不符，并提供可见诊断。

**涉及：** `🚫格式顺序`、`⚓️尾部`、相关正则；只有需要自动校验时才新增脚本。

### P3-1：消息重组先验证，再替换

命定按标记区分头部、世界资料、历史、深层记忆、近层运行规则和尾部；脚本将主体合并成 user 消息，并检查边界是否齐全。这个分区思路有价值，但本卡已有 kemini 合并逻辑与 SPreset。

如重构，应保证只有一个组件负责改写请求消息；明确只处理正文请求，避免误处理 MVU 额外请求、总结、人物精修和提示词预览。命定的处理脚本会拒绝与仍在运行的旧 SPreset 共存，不能直接叠加安装。

验收应检查实际请求中的消息角色、顺序和内容；“显示三条消息”本身不是性能或效果指标。

### P3-2：讨论模式必须隔离结算

命定的讨论模式不只是改一句角色身份，还切换输出协议，并将原世界规则标注为讨论材料。

本卡现有 `⚓️拷打模式(Gemini)` 只提供任务切换文本，不宜据此认为已经完成场外讨论隔离。如果需要正式讨论模式，应同时处理正文渲染、MVU、总结和路由，防止分析中的示例 JSON Patch 或试写被当作真实剧情结算。

### P3-3：将设置互斥关系做成明确约束

模型入口三选一、变量模式二选一，以及抢话/转述/对白的依赖关系，可由设置界面或校验器统一管理。不要把“条目名称写了二选一”当成运行时已经保证互斥。

本轮仅调整入口与使用说明，没有新增设置界面，也没有移植命定的远程预设助手。

## 6. 建议实施顺序与比较方法

1. 先使用本轮统一短链版本，确认三个模型、两种变量模式的结构正常。
2. 优先做动作依赖、待结算事实和规则触发边界。
3. 再调整对白、篇幅和文风，避免同时改变太多因素而无法判断效果。
4. 最后考虑消息处理与正式讨论模式，这两项需要跨预设、脚本和界面联调。

对比使用相同聊天快照、输入、模型和连接设置。若验证数值行为，还需记录或固定测试骰池；否则随机结果不同不能直接归因于预设修改。测试副本与实际游玩存档分开。

| 用例 | 重点检查 |
| --- | --- |
| 普通交谈、独处修炼 | 不无故生成战斗/生产面板，不为对白比例抢话 |
| 买丹、服丹、突破的连续输入 | 前提失败后停止依赖步骤 |
| 战斗一回合、失败的生产 | 不预判成功，不超回合，不重复扣除 |
| 世界推进及其重生成/续写 | 区间不变、时间点正确、无重复结算 |
| 死亡与轮回转生 | 保留本卡分流规则，不套用命定复活机制 |
| 主 API / 额外 API | 更新职责正确、标签完整、变化与事实一致 |
| Claude 英文规划 | 七步齐全，路由过滤一致，正文仍为中文 |

观察指标：格式完整率、遗漏/误触发面板、错误变量更新、重复扣除、抢话、正文长度、可见规划长度与生成耗时。没有实际生成样本前，不宣称这些建议已提升模型效果。
