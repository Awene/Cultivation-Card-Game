# 日常类事件编写经验

> 本文总结萝武门、广寒宫日常事件的设计与落地经验，适用于宗门生活、人物邂逅、轻量伏笔等“一轮即结”的小型事件。通用事件机制仍以 [事件写作规范.md](事件写作规范.md) 和 [[模板]小型事件骨架.txt](../世界书/事件/[模板]小型事件骨架.txt) 为准。

## 一、先确定事件的职责

日常事件的目标是让宗门显得有人生活，而不是承担完整主线。一个合格的日常事件通常只完成一件事：

- 展现一种宗门日常，例如夜课、药浴、采集、晨练或整理功课。
- 展现人物性格的一个侧面，例如嘴硬、好胜、怕黑、疲惫时仍认真做事。
- 留下一个可由玩家继续推动的小问题，但不在本轮替玩家解决。

如果事件需要连续调查、跨场景行动、重大抉择或多种结局，应改用大型事件状态机，不要把整条支线压进一次日常触发。

## 二、先分清“群体事件”和“人物专属事件”

这是宗门日常最重要的登场控制。

### 1. 群体事件

群体事件用于表现宗门共同生活，例如萝武门“初次共浴”、广寒宫“初次夜课”和“晶蝶停翅”。

写作要求：

- 不点名任何尚未确认在当前故事中登场的人物。
- 使用“同门”“师姐”“同期”“值守弟子”“授课长老”“全部弟子”等模糊称谓。
- 被闲谈或调侃的人也尽量使用职务、辈分等匿名称谓，避免一句八卦把未登场角色提前拉入剧情。
- 可以写三至五段交错对话，但对话者始终保持匿名，不临时生成新姓名。
- 群体的重点是生活气氛、门内秩序和共同习惯，不是逐个介绍角色。

错误示例：第一次共浴时直接列出掌门、脉主和数名弟子的姓名。这样会默认所有角色已经与玩家相识。

正确思路：写值守弟子检查药汤、同期给玩家留位置、师姐谈论晨课糗事；具体是谁，等人物真正登场后再确定。

### 2. 人物专属事件

人物专属事件用于建立 `{{user}}` 与某个既定人物之间的生活联系。

写作要求：

- 当前场景只允许 `{{user}}` 与该人物实际参与。
- 开场先说明其他人已经离开、附近无人或场地已经空下，堵住模型临时召来第三人的可能。
- 不使用“叫其他弟子来帮忙”“让某某代为转交”等需要第三人入场的解决方案。
- 允许提到已故者、过去发生的事或不在场的匿名同门，但他们只能是背景信息，不能在当前场景说话或行动。
- 结尾再次明确“不召来第三人”“当前场景只保留两人”，提高模型执行稳定性。

萝武门“蜂蜜药浴”的处理经验尤其典型：若把黎甘棠与整池弟子同时写入，事件既像群体日常又像人物专属，焦点会散。改成共同药浴散场后，`{{user}}` 因遗落物品折返，只剩黎甘棠核对空坛，既保留蜂蜜乌龙，也保证角色登场可控。

## 三、让事件具有生活气息，而不是人物说明书

生活感来自具体动作、物件和小麻烦。

- 用可触摸的物件承载情节：凉掉的面、打结的剑穗、熄灭的油灯、放错的蜂蜜坛、晒暖的被褥。
- 用连续动作表现性格：先核对药册再承认失误，比直接写“她很认真”更有效。
- 冲突宜小而真实：困倦、手笨、害怕黑暗、误拿物品、好胜却不愿占便宜。
- 人物能力不能为了制造笑点突然消失。医者应先确认药浴安全，负责人会补写记录，修士也应有符合身份的处理方式。
- 玩笑不能破坏宗门基调。广寒宫不等于人人冷漠，萝武门也不等于只会粗暴锻体；日常事件应补足设定，而不是把单一标签夸张到底。

## 四、保留玩家的行动权

事件正文负责把场景推到“轮到玩家回应”的位置，然后停止。

- 不替 `{{user}}` 说话、追问、安慰、答应或拒绝。
- 给出两至四种自然方向作为提示，但不写成强制按钮。
- 人物可以提出请求、暴露困境或等待回答，不能自动替玩家完成互动。
- 需要开放后续时，应明确写“到此停下，下一轮由 `{{user}}` 推动”。
- 日常事件不应自动兑换为表白、道侣关系、考核名次、额外奖励或重大秘密。

## 五、触发器要具体、互斥并有优先级

一轮即结事件应满足以下基本门禁：

1. 当前没有大型事件进行：`标题 === ''`。
2. 玩家具有本宗身份。
3. 当前处于宗门相关地点。
4. `事件.已完成事件` 中尚无本事件令牌。
5. 命中人物、地点、活动或时间关键词。

同一文件中用 `本轮已触发` 保证每轮最多输出一个事件。具有明确首次体验性质的事件应排在最前，例如第一次共浴、第一次夜课，避免被后面的随机事件抢占。

关键词应围绕真实触发语境组合：

- 人物专属事件优先包含人物名，再搭配地点或活动词。
- 群体事件使用宗门地标与活动词，不依赖人物名。
- 夜间事件同时检查时辰与“入夜、夜里、月下”等自然语言。
- 随机概率只用于提高偶遇率，不能绕过身份、地域、大事件占用和已完成门禁。

## 六、完成令牌必须稳定写入

每个小事件末尾只写入一次唯一令牌：

```json
{ "op": "insert", "path": "/事件/已完成事件/-", "value": "宗门名·事件名" }
```

注意事项：

- `事件.已完成事件` 必须在变量初始化中存在且类型为数组。
- 触发判断与写入值必须逐字一致。
- 同一个令牌不能出现在多个事件中。
- 小事件不占用 `事件.标题` 和 `事件.阶段`，否则会无故阻塞大型事件。
- 已完成事件必须彻底静默，避免每轮重复输出同一条插入命令。

## 七、正文中的导演指令要明确

模型容易在留白处自行补人、补秘密或补严重后果，因此关键限制应直接写进事件正文或注释：

- “所有同门均使用模糊称谓，不生成姓名。”
- “当前场景只保留 `{{user}}` 与该人物。”
- “不召来第三人，也不让其他角色进入场景。”
- “后续开放留白，不替 `{{user}}` 推动。”
- “传闻必须明确只是听说，不写成已确认事实。”
- “不造成异常药效或伤害。”

这些不是多余说明，而是控制实际生成结果的护栏。

## 八、推荐的编写流程

1. 查阅宗门总览、人物条目和既有地标，只使用已经存在的设定。
2. 列出事件清单，并标记每项是“匿名群体”还是“人物专属”。
3. 为每个事件只选一个生活矛盾或人物侧面。
4. 先写触发条件和完成令牌，再写正文，避免故事写完后才补机制。
5. 检查人物能力、身份职责、时间与地点是否合理。
6. 检查是否替玩家作出决定，是否在专属事件中引入第三人。
7. 实际渲染所有触发分支，而不只做文本检查。

## 九、验证清单

提交前至少验证：

- EJS 能正常编译。
- 无事件条件下输出为空。
- 每个测试语境只渲染一个 `<event>`。
- 群体事件的渲染结果不含任何既定人物姓名。
- 人物专属事件只含目标人物姓名，不含同宗其他具名角色。
- 每个事件只出现一次对应的完成令牌。
- 已完成后不会再次触发。
- 大型事件进行中，全部日常事件保持静默。
- `git diff --check` 无空白或补丁格式错误。

## 十、常见失败与修正方式

| 失败表现 | 原因 | 修正方式 |
| --- | --- | --- |
| 群体活动一次点出全部人物 | 把日常事件当成角色介绍页 | 全部改为匿名同门与职务称谓 |
| 专属事件中途叫来其他人 | 缺少场景封闭和结尾限制 | 开场清场，结尾明确只有两人参与 |
| 人物为了笑点显得失职 | 只顾桥段，没有考虑身份能力 | 先让人物完成必要的安全检查与职责 |
| 一轮内自动发展成重大关系 | 没有在可互动节点停下 | 把结尾停在问题、请求或等待回应处 |
| 同轮出现多个事件 | 各事件独立判断，没有互斥标记 | 使用 `本轮已触发` 并安排优先级 |
| 事件每轮重复出现 | 完成令牌未写入或变量容器不存在 | 初始化数组，统一判断值与写入值并做渲染测试 |

一句话概括：**群体事件写宗门的生活，专属事件写两个人的关系；每次只推进一小步，把下一步留给玩家。**
