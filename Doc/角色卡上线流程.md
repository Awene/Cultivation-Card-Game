# 本格修仙角色卡上线流程

本文记录一次完整的正式版上线流程。前端发布和角色卡打包是两个独立步骤，均需手动执行：

1. `tavern_helper_template-main` 在本地构建前端，提交 `dist`，手动创建并推送版本 tag。
2. `Cultivation-Card-Game` 把正式指针更新到该 tag，再手动生成角色卡 PNG。

普通 `git push` 不会自动打包前端，也不会自动生成角色卡 PNG。

前端打包工作流 `.github/workflows/bundle.yaml` 已从本地流程中移除；该删除提交推送至远端 `main` 后生效。远端尚未同步时，请勿运行旧的 `manual bundle`。依赖更新与模板同步工作流不属于发布步骤，保持原有用途。

本流程只在明确执行正式上线时运行。日常开发、修改本文或本地构建不等于发布，不应顺带触发工作流、修改正式指针或覆盖发布 PNG。

一次发布必须核对完整链路：**本次源码提交 → 本地构建及新 tag 产物 → CDN 内容 → 角色卡源文件指针 → PNG 内嵌指针 → 导入后的本次功能效果**。六处指针一致、CDN 返回 200、PNG 修改时间更新，均不能单独证明新功能已经上线。

## 一、发布前检查

先检查两个仓库的分支、工作区和已有改动：

```powershell
git status --short
git branch --show-current
git ls-remote --symref origin HEAD
git ls-remote --heads origin
```

不要在存在来源不明的未提交改动时直接打包。正式版不得引用 `localhost`、分支名或 `@latest`；必须使用不可变版本 tag，例如 `@v1.0.53`。

两个仓库当前正式分支均为 `main`。不能仅凭本地分支或旧的 `origin/HEAD` 判断远端默认分支；分支迁移后，应先核对上述远端查询，再切换到并跟踪实际发布分支。构建使用 Node.js 24、pnpm 10，避免本机其他大版本自动迁移配置。

辨认并保留已有改动，工作区适合更新时再执行 `git pull --rebase`；不要为发布清空用户改动。核对实际工作流、分支与资源入口，本文的文件清单应随项目变化更新。

在 `Doc` 中记录本次发布的版本、前端源码提交 SHA、角色卡构建输入提交 SHA、本地构建命令与结果、新 tag 及目标 SHA、最终 PNG 的 SHA-256，以及本次新增/修复功能的验收结果。未执行的检查明确记为“未验证”，不得宣称完整上线成功。如本次涉及路由插件或后端，还需记录其提交、部署版本和联调结果；前端发布不代表后端已更新。

### 构建输入的先后顺序

人物细化等功能在构建时读取本地相邻的 `Cultivation-Card-Game` 仓库中的世界书与提示词。两个仓库须位于同一父目录，并保留现有目录名。**先确认并提交本次需要进入前端构建的角色卡规则，再构建前端**；此时正式指针与 PNG 可继续保留上一版，待新前端验证完成后再更新。

记录构建实际使用的两个仓库 SHA，确认参与构建的文件没有未提交改动。构建期间保持本地输入不变；后续源码或规则改动若影响构建输入，重新构建和验证。正式发布前将对应源码提交推送至远端。

## 二、提交源码并在本地构建前端

先检查远端已有 tag，选定尚未使用的版本号（通常递增补丁号），后文统一用 `<新版本>` 表示。将地图等源码中的固定资源地址调整至本次版本，完成源码检查后，按实际范围提交源码并记录 SHA。

在 `tavern_helper_template-main` 仓库执行，任一命令失败即停止后续发布步骤：

```powershell
pnpm install --frozen-lockfile
pnpm dump
pnpm lint
pnpm build:frontend
```

检查重点：

- 修仙状态栏的普通模式和编辑模式均可使用。
- 桌面宽度与手机窄屏下没有横向溢出。
- 自定义开局、正文美化和状态栏的日间/夜间模式可以同步。
- 浏览器控制台没有新增错误。
- 地图等附属资源也应固定版本；当前 `src/修仙状态栏/pages/PageMap.vue` 的地图根地址须与本次发布 tag 一同核对，不得保留 `@latest`。
- `git diff --check` 通过。

`build:frontend` 构建全部前端入口，但不调用 `tavern_sync` 打包角色卡。普通 `pnpm build` 保留模板原行为，发布前端时使用 `pnpm build:frontend`。

源码提交示例（在上述构建前完成）：

```powershell
git add src
git commit -m "feat: 描述本次前端更新"
```

如本次还修改了工作流、配置或其他必要文件，应明确加入提交，不要机械使用 `git add .`。

记录前端源码 SHA，并核对构建产生的 `dist` 与 schema 等文件变化；若构建还改变了参与编译的源码，应审核、提交后重新构建。旧 tag 不会自动包含新提交，仍须完成下列产物提交与版本验证。

## 三、手动发布前端版本

审核并提交本次生产构建产物，版本 tag 必须落在包含产物的提交上：

```powershell
git status --short
git diff --check
git diff --stat -- dist
git add dist
git commit -m "build: 手动构建前端 <新版本>"
git rev-parse HEAD
```

记录上述产物提交 SHA。如产物无变化，确认原因并记录，可直接使用已核实的提交。`dist` 中的静态地图、封面等资源须保留；示例入口不属于正式发布内容，只暂存本次需要发布的文件，不直接清空整个 `dist`。

确认版本未被占用后，手动创建附注 tag 并推送：

```powershell
git fetch --tags
git tag --sort=-version:refname | Select-Object -First 5
git ls-remote origin 'refs/tags/<新版本>'
git tag -a <新版本> <本次产物提交SHA> -m "前端 <新版本>"
git push --atomic origin main refs/tags/<新版本>
```

以上尖括号内容均须替换为本次实际值。若推送被拒绝，核对远端变化；如需合并或变基，重新构建、审核产物后确定发布提交，不强制推送。核对以下关系：

```powershell
git rev-parse '<新版本>^{commit}'
git merge-base --is-ancestor <本次前端源码SHA> <新版本>
if ($LASTEXITCODE -ne 0) { throw '新 tag 不包含本次源码，停止发布' }
git ls-remote origin 'refs/tags/<新版本>' 'refs/tags/<新版本>^{}'
```

本地与远端 tag 必须一致，附注 tag 比较解引用后的提交，目标须为本次核实的产物提交。祖先检查只证明源码已包含，仍须检查 **tag 内的 `dist`** 是否包含本次功能，不能用工作区 `dist` 代替。保留所有历史 tag，确保旧角色卡仍能加载原版本资源。

## 四、验证 CDN 产物

在更新角色卡指针前，逐一确认以下资源返回 HTTP 200：

```text
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/修仙状态栏/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/自定义开局/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/正文美化/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/创意工坊/index.js
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/楼层iframe回收/index.js
```

可以直接用浏览器访问，也可执行：

```powershell
curl.exe -I "上面的完整 URL"
```

如果 tag 已存在但 CDN 暂时无法访问，先等待缓存同步，不要把角色卡指向尚未验证的地址。

HTTP 200 只证明资源可访问。还必须 GET 下载上述资源，确认返回的是 HTML/JavaScript 而非错误页，并逐一与新 tag 中对应 `dist` 文件比较内容或 SHA-256。比较应基于原始文件字节，避免 PowerShell 文本重编码改变哈希；若有差异，查明原因后再继续。页面引用的附属资源也须正常加载。

为本次变化选取可辨认的产物特征，并用浏览器验证行为。例如技艺界面改造应确认名称与数字徽章位置、旧进度环已移除、大数字缩写与配方展开生效；“状态栏能够打开”不能代替这些检查。若测试使用 localhost，须另行验证固定 tag 的正式 CDN 入口。

## 五、更新角色卡正式指针

在 `Cultivation-Card-Game` 中更新下列文件：

| 文件 | 指向的资源 |
| --- | --- |
| `正则/状态栏.txt` | 修仙状态栏 |
| `正则/自定义开局.txt` | 自定义开局 |
| `正则/正文美化.txt` | 正文页面和 `__rb_asset_base`，共两处 |
| `脚本/【本格修仙】创意工坊.js` | 创意工坊 |
| `本格修仙.yaml` | 楼层 iframe 回收 |

当前清单一共应有 6 处 `tavern_helper_template-main@<版本>` 正式引用，必须全部使用第三、四节已验证的本次 tag；不能只检查六处彼此相同：

```powershell
rg -n -F "Awene/tavern_helper_template-main@" 正则 脚本 本格修仙.yaml
```

在上述五个正式源文件中再搜索上一个版本号，结果应为 0；历史记录和发布文档保留旧版本是正常的。测试文件中的 `http://localhost:5500` 是本地调试入口，应保持不变。若资源入口增减，先更新清单和预期数量，再逐项核验，不机械凑足六处。

完成后检查文本和脚本：

```powershell
git diff --check
node --check "脚本/【本格修仙】创意工坊.js"
git diff
```

## 六、手动生成角色卡 PNG

确认前端 tag、CDN 和角色卡指针全部正确后，在角色卡仓库根目录手动执行：

```powershell
node tavern_sync.mjs bundle 本格修仙
```

该命令会覆盖仓库根目录的 `本格修仙.png`。执行前应确认路径和工作区状态，不要把旧发布成品误当作可恢复备份。

打包完成后确认：

```powershell
git status --short
Get-Item "本格修仙.png" | Select-Object Name,Length,LastWriteTime
Get-FileHash -LiteralPath "本格修仙.png" -Algorithm SHA256
```

文件大小和修改时间仅作辅助。必须用支持角色卡元数据的工具或只读 PNG 解析脚本，解码 PNG 中的 `chara`/`ccv3` 数据并解析 JSON，检查内嵌正则和脚本的实际 URL：

- 五个正式入口对应的六处引用均为本次 tag，正文美化的页面 URL 和资源基址都要检查。
- 正式启用的入口中没有旧 tag、localhost 或浮动分支地址；检查各入口的启用状态，避免正式与测试入口同时生效。
- 若 PNG 同时含 `chara` 与 `ccv3`，分别检查，确保不存在导入器读取另一份旧数据的情况。
- 本次规则或脚本修改也已进入内嵌数据，不能只核对 URL。

PNG 字段结构可能含兼容副本，不按整个 JSON 的字符串总出现次数机械判断“六处”，而是按实际入口逐项核对。发现不一致时回到源文件与打包配置排查，再重新生成、验证并记录哈希。

## 七、导入酒馆做最终冒烟测试

用新生成的 PNG 新建一份角色卡进行测试，避免旧聊天或浏览器缓存掩盖问题。至少检查：

- 自定义开局能够加载和完成开局。
- 状态栏能够读取 MVU 数据。
- 功法位于储物页，与物品、装备、傀儡、灵兽同级。
- 资产页显示、编辑、新增、删除均正常。
- 人员规模显示为“规模：N人”。
- 正文美化能够渲染，原始正文回退逻辑可用。
- 三处主题切换保持同步。
- 创意工坊可以打开。
- 切换楼层后旧 iframe 能够正确回收。
- 浏览器控制台没有资源 404 或新增异常。

除以上通用检查，必须逐项验收第一节记录的本次功能变化，并覆盖涉及的桌面与手机布局。通过浏览器 Network 确认实际加载的 URL 使用本次固定 tag，不能仅凭页面外观推断版本。记录测试 PNG 的哈希、入口 URL 和结果；无法进行浏览器测试时标记“待验收”，不要把源码或静态产物检查描述成已完成冒烟测试。

如果条件允许，再用一份旧角色卡确认历史 tag 仍可加载，避免新发版破坏旧用户。

## 八、提交并上线角色卡

最终检查本次提交范围，只纳入确实需要发布的源码和手动生成的 PNG：

```powershell
git status --short
git diff --check
git add 本格修仙.yaml 本格修仙.png 正则 脚本
git commit -m "release: 更新角色卡至 <新版本> 前端"
git push origin main
```

如通过其他平台分发角色卡，上传刚刚生成并验证过的同一份 `本格修仙.png`，不要再次临时打包产生未经测试的不同文件。

提交范围还应包含本次需要上线的世界书、预设、构建配置等实际改动和发布记录，上述 `git add` 示例不是完整文件清单。推送后核实远端角色卡提交、前端 tag 与发布记录一致，核对分发 PNG 的 SHA-256 与已测试文件相同。若验收后又修改源码、指针或 PNG，重新执行受影响的构建与验收步骤。

## 九、回滚原则

- 不删除或移动已经发布的前端历史 tag。
- 新版本异常时，把五个源文件中的指针恢复到上一个已验证 tag，重新手动生成 PNG。
- 不使用 `@master`、`@main` 或 `@latest` 代替固定 tag。
- 不通过覆盖旧 tag 来修补产物；修复源码后发布一个新 tag。
