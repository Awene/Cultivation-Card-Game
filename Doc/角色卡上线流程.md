# 本格修仙角色卡上线流程

本文记录一次完整的正式版上线流程。前端发布和角色卡打包是两个独立步骤，均需手动执行：

1. `tavern_helper_template-main` 在本地构建前端，提交 `dist`，手动创建并推送版本 tag。
2. `Cultivation-Card-Game` 把正式指针更新到该 tag，更新交付版本，打包角色卡与预设，并复制路由插件配置，归档三份交付物。
3. `cultivation-rule-router` 提交并推送本次路由插件改动，核对用户可更新到的远端版本。

**每次上线都必须完成三个仓库的 Git 发布**：`tavern_helper_template-main`、`Cultivation-Card-Game`、`cultivation-rule-router`。分别提交本次相关改动并推送各自正式分支；前端产物有变化时还须推送本次版本 tag；产物未变则沿用已验证的旧 tag。某仓库没有新改动时，不创建空提交，但必须确认本地发布提交已在远端，并记录 SHA。不要把用户无关的工作区改动一并提交。

普通 `git push` 不会自动打包前端，也不会自动生成角色卡 PNG。

前端打包工作流 `.github/workflows/bundle.yaml` 已从本地流程中移除；该删除提交推送至远端 `main` 后生效。远端尚未同步时，请勿运行旧的 `manual bundle`。依赖更新与模板同步工作流不属于发布步骤，保持原有用途。

本流程只在明确执行正式上线时运行。日常开发、修改本文或本地构建不等于发布，不应顺带触发工作流、修改正式指针或覆盖发布 PNG。

一次发布必须核对完整链路：**本次源码提交 → 本地构建及新 tag 产物 → CDN 内容 → 角色卡源文件指针 → PNG 内嵌指针 → 导入后的本次功能效果**。六处指针一致、CDN 返回 200、PNG 修改时间更新，均不能单独证明新功能已经上线。

## 一、发布前检查

### 交付版本与命名

发布批次目录从 `Ver.1.0` 开始递增。三份交付物各自维护版本：以各自上次交付文件为基准，内容变化才递增（例如 `Ver.1.0` → `Ver.1.1`）；本次打包结果与上次字节完全一致时，沿用旧版本、旧文件名和原文件字节。一个批次目录可以同时包含不同版本的文件。交付版本独立于前端 Git tag；后文 `<新版本>` 仍指前端 tag。

先保留原版本号生成候选产物，与上次交付文件比较 SHA-256。完全一致则复用原文件；有差异先核查原因，不因时间戳、序列化或自动构建噪声盲目升版。确认角色卡内容变化后，才更新 `本格修仙.yaml` 第 3 行的 `版本` 字段并重新打包。不要先改版本号再把版本号本身造成的差异当作升版依据。预设、路由配置也按各自实际变更决定版本；不得仅因发布日期变化刷新组件修订号。日常开发和仅修改流程时不递增交付版本、不生成发布文件夹。

最终交付目录以首版为例：

```text
发布文件/Ver.1.0/
├── 本格修仙preset-Ver.1.0.json
├── 本格修仙 Ver.1.0.png
└── 本格修仙router-config-Ver.1.0.json
```

PNG 名称只包含一次 `Ver.`。预设必须是酒馆可直接导入的 JSON，不能交付拆分的 `index.yaml`。路由配置复制自 `插件/cultivation-rule-router-config.json`。

### 日常测试预设

在角色卡仓库执行 `node tavern_sync.mjs push 本格修仙预设 -f`，目标为酒馆中的 `本格修仙preset-test`。本地源文件仍为 `预设/本格修仙/index.yaml`，默认 bundle 文件为 `预设/本格修仙/本格修仙-test.json`。正式发布时复制并重命名打包结果，不修改测试推送目标。

先分别检查三个仓库的分支、工作区和已有改动：

```powershell
git status --short
git branch --show-current
git ls-remote --symref origin HEAD
git ls-remote --heads origin
```

不要在存在来源不明的未提交改动时直接打包。正式版不得引用 `localhost`、分支名或 `@latest`；必须使用不可变版本 tag，例如 `@v1.0.53`。

三个仓库当前正式分支均为 `main`。不能仅凭本地分支或旧的 `origin/HEAD` 判断远端默认分支；分支迁移后，应先核对上述远端查询，再切换到并跟踪实际发布分支。构建使用 Node.js 24、pnpm 10，避免本机其他大版本自动迁移配置。

辨认并保留已有改动，工作区适合更新时再执行 `git pull --rebase`；不要为发布清空用户改动。核对实际工作流、分支与资源入口，本文的文件清单应随项目变化更新。

在 `Doc` 中记录本次发布的版本、前端源码提交 SHA、角色卡构建输入提交 SHA、本地构建命令与结果、新 tag 及目标 SHA、最终 PNG 的 SHA-256，以及本次新增/修复功能的验收结果。未执行的检查明确记为“未验证”，不得宣称完整上线成功。如本次涉及路由插件或后端，还需记录其提交、部署版本和联调结果；前端发布不代表后端已更新。

### 构建输入的先后顺序

人物细化等功能在构建时读取本地相邻的 `Cultivation-Card-Game` 仓库中的世界书与提示词。两个仓库须位于同一父目录，并保留现有目录名。**先确认并提交本次需要进入前端构建的角色卡规则，再构建前端**；此时正式指针与 PNG 可继续保留上一版，待新前端验证完成后再更新。

记录构建实际使用的两个仓库 SHA，确认参与构建的文件没有未提交改动。构建期间保持本地输入不变；后续源码或规则改动若影响构建输入，重新构建和验证。正式发布前将对应源码提交推送至远端。

## 二、提交源码并在本地构建前端

先检查远端已有 tag，选定尚未使用的版本号（通常递增补丁号），后文统一用 `<新版本>` 表示。将地图等源码中的固定资源地址调整至本次版本，完成源码检查后，按实际范围提交源码并记录 SHA。

在 `tavern_helper_template-main` 仓库执行，任一命令失败即停止后续发布步骤：

```powershell
pnpm install --frozen-lockfile
pnpm dump
pnpm lint
pnpm build:frontend
```

检查重点：

- 修仙状态栏的普通模式和编辑模式均可使用。
- 桌面宽度与手机窄屏下没有横向溢出。
- 自定义开局、正文美化和状态栏的日间/夜间模式可以同步。
- 浏览器控制台没有新增错误。
- 地图等附属资源也应固定版本；当前 `src/修仙状态栏/pages/PageMap.vue` 的地图根地址须与本次发布 tag 一同核对，不得保留 `@latest`。
- `git diff --check` 通过。

`build:frontend` 构建全部前端入口，但不调用 `tavern_sync` 打包角色卡。普通 `pnpm build` 保留模板原行为，发布前端时使用 `pnpm build:frontend`。

源码提交示例（在上述构建前完成）：

```powershell
git add src
git commit -m "feat: 描述本次前端更新"
```

如本次还修改了工作流、配置或其他必要文件，应明确加入提交，不要机械使用 `git add .`。

记录前端源码 SHA，并核对构建产生的 `dist` 与 schema 等文件变化；若构建还改变了参与编译的源码，应审核、提交后重新构建。旧 tag 不会自动包含新提交，仍须完成下列产物提交与版本验证。

## 三、手动发布前端版本

审核并提交本次生产构建产物，版本 tag 必须落在包含产物的提交上：

```powershell
git status --short
git diff --check
git diff --stat -- dist
git add dist
git commit -m "build: 手动构建前端 <新版本>"
git rev-parse HEAD
```

记录上述产物提交 SHA。如产物无变化，确认原因并记录，复用已核实的旧 tag，不创建新版本。先比较实际产物，再决定是否更新地图等固定资源指针，避免仅修改版本 URL 制造变化。`dist` 中的静态地图、封面等资源须保留；示例入口不属于正式发布内容，只暂存本次需要发布的文件，不直接清空整个 `dist`。

确认版本未被占用后，手动创建附注 tag 并推送：

```powershell
git fetch --tags
git tag --sort=-version:refname | Select-Object -First 5
git ls-remote origin 'refs/tags/<新版本>'
git tag -a <新版本> <本次产物提交SHA> -m "前端 <新版本>"
git push --atomic origin main refs/tags/<新版本>
```

以上尖括号内容均须替换为本次实际值。若推送被拒绝，核对远端变化；如需合并或变基，重新构建、审核产物后确定发布提交，不强制推送。核对以下关系：

```powershell
git rev-parse '<新版本>^{commit}'
git merge-base --is-ancestor <本次前端源码SHA> <新版本>
if ($LASTEXITCODE -ne 0) { throw '新 tag 不包含本次源码，停止发布' }
git ls-remote origin 'refs/tags/<新版本>' 'refs/tags/<新版本>^{}'
```

本地与远端 tag 必须一致，附注 tag 比较解引用后的提交，目标须为本次核实的产物提交。祖先检查只证明源码已包含，仍须检查 **tag 内的 `dist`** 是否包含本次功能，不能用工作区 `dist` 代替。保留所有历史 tag，确保旧角色卡仍能加载原版本资源。

## 四、验证 CDN 产物

在更新角色卡指针前，逐一确认以下资源返回 HTTP 200：

```text
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/修仙状态栏/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/自定义开局/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/正文美化/index.html
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/创意工坊/index.js
https://testingcf.jsdelivr.net/gh/Awene/tavern_helper_template-main@<新版本>/dist/楼层iframe回收/index.js
```

可以直接用浏览器访问，也可执行：

```powershell
curl.exe -I "上面的完整 URL"
```

如果 tag 已存在但 CDN 暂时无法访问，先等待缓存同步，不要把角色卡指向尚未验证的地址。

HTTP 200 只证明资源可访问。还必须 GET 下载上述资源，确认返回的是 HTML/JavaScript 而非错误页，并逐一与新 tag 中对应 `dist` 文件比较内容或 SHA-256。比较应基于原始文件字节，避免 PowerShell 文本重编码改变哈希；若有差异，查明原因后再继续。页面引用的附属资源也须正常加载。

为本次变化选取可辨认的产物特征，并用浏览器验证行为。例如技艺界面改造应确认名称与数字徽章位置、旧进度环已移除、大数字缩写与配方展开生效；“状态栏能够打开”不能代替这些检查。若测试使用 localhost，须另行验证固定 tag 的正式 CDN 入口。

在 `Cultivation-Card-Game` 中更新下列文件：

```powershell
rg -n -F "Awene/tavern_helper_template-main@" 正则 脚本 本格修仙.yaml
```

完成后检查文本和脚本：

```powershell
git diff --check
node --check "脚本/【本格修仙】创意工坊.js"
git diff
```

## 六、打包并归档三份交付物

确认前端 tag、CDN 和角色卡指针全部正确后，先保留角色卡原版本，在角色卡仓库根目录生成候选产物并逐项比较；确认变化后按第一节规则更新对应版本，再重新打包：

```powershell
node tavern_sync.mjs bundle 本格修仙
node tavern_sync.mjs bundle 本格修仙预设
```

该命令会覆盖仓库根目录的 `本格修仙.png`。执行前应确认路径和工作区状态，不要把旧发布成品误当作可恢复备份。

打包完成后确认：

```powershell
git status --short
Get-Item "本格修仙.png" | Select-Object Name,Length,LastWriteTime
Get-FileHash -LiteralPath "本格修仙.png" -Algorithm SHA256
```

文件大小和修改时间仅作辅助。必须用支持角色卡元数据的工具或只读 PNG 解析脚本，解码 PNG 中的 `chara`/`ccv3` 数据并解析 JSON，检查内嵌正则和脚本的实际 URL：

- 五个正式入口对应的六处引用均为本次 tag，正文美化的页面 URL 和资源基址都要检查。
- 正式启用的入口中没有旧 tag、localhost 或浮动分支地址；检查各入口的启用状态，避免正式与测试入口同时生效。
- 若 PNG 同时含 `chara` 与 `ccv3`，分别检查，确保不存在导入器读取另一份旧数据的情况。
- 本次规则或脚本修改也已进入内嵌数据，不能只核对 URL。

PNG 字段结构可能含兼容副本，不按整个 JSON 的字符串总出现次数机械判断“六处”，而是按实际入口逐项核对。发现不一致时回到源文件与打包配置排查，再重新生成、验证并记录哈希。

同时确认 PNG 内嵌角色卡版本与该 PNG 的文件版本一致（不要求等于发布批次号）。检查预设 JSON 可解析，包含本次最新提示词、条目开关与设置；路由配置 JSON 也须可解析。

将以下示例中的版本改为本次交付版本，再归档。每个 bundle 命令均须成功后才能继续，不能复制失败后残留的旧产物。

```powershell
# 示例：本批次只更新角色卡，预设与路由配置完全未变。
$releaseVersion = 'Ver.1.1'
$cardVersion = 'Ver.1.1'
$presetVersion = 'Ver.1.0'
$routerVersion = 'Ver.1.0'
$releaseDir = Join-Path '发布文件' $releaseVersion
if (Test-Path -LiteralPath $releaseDir) { throw '该版本目录已存在，请核对版本，不覆盖历史交付物' }
New-Item -ItemType Directory -Path $releaseDir | Out-Null
Copy-Item -LiteralPath '发布文件/Ver.1.0/本格修仙preset-Ver.1.0.json' -Destination (Join-Path $releaseDir "本格修仙preset-$presetVersion.json")
Copy-Item -LiteralPath '本格修仙.png' -Destination (Join-Path $releaseDir "本格修仙 $cardVersion.png")
Copy-Item -LiteralPath '发布文件/Ver.1.0/本格修仙router-config-Ver.1.0.json' -Destination (Join-Path $releaseDir "本格修仙router-config-$routerVersion.json")
Get-ChildItem -LiteralPath $releaseDir -File | Get-FileHash -Algorithm SHA256
```

有变化的文件从本次构建结果或配置源文件复制；未变化的文件从上次交付目录原样复制。版本目录中最终仅放三份文件；发布记录留在 `Doc`，逐项列明文件版本、是否变化、上次与本次 SHA-256，并确认路由配置副本与源文件一致。

## 七、导入酒馆做最终冒烟测试

使用本次 `发布文件/Ver.x.y/` 中的三份交付物进行测试：导入 PNG 新建角色卡，导入预设 JSON，并在路由插件中导入路由配置 JSON。确认三者均可导入、预设内容为本次版本、路由配置生效，避免旧聊天或浏览器缓存掩盖问题。至少检查：

- 自定义开局能够加载和完成开局。
- 状态栏能够读取 MVU 数据。
- 功法位于储物页，与物品、装备、傀儡、灵兽同级。
- 资产页显示、编辑、新增、删除均正常。
- 人员规模显示为“规模：N人”。
- 正文美化能够渲染，原始正文回退逻辑可用。
- 三处主题切换保持同步。
- 创意工坊可以打开。
- 切换楼层后旧 iframe 能够正确回收。
- 浏览器控制台没有资源 404 或新增异常。

除以上通用检查，必须逐项验收第一节记录的本次功能变化，并覆盖涉及的桌面与手机布局。通过浏览器 Network 确认实际加载的 URL 使用本次固定 tag，不能仅凭页面外观推断版本。记录测试 PNG 的哈希、入口 URL 和结果；无法进行浏览器测试时标记“待验收”，不要把源码或静态产物检查描述成已完成冒烟测试。

如果条件允许，再用一份旧角色卡确认历史 tag 仍可加载，避免新发版破坏旧用户。

## 八、提交并上线角色卡

最终检查本次提交范围，只纳入确实需要发布的源码、打包产物与本次交付目录：

```powershell
git status --short
git diff --check
git add 本格修仙.yaml 本格修仙.png 正则 脚本
git add "发布文件/<交付版本>"
git commit -m "release: 更新角色卡至 <新版本> 前端"
git push origin main
```

如通过其他平台分发，上传本次版本目录内已经验证的三份交付物，保留版本化文件名，不再临时打包产生未经测试的不同文件。将 `<交付版本>` 替换为例如 `Ver.1.0`。

提交范围还应包含本次需要上线的世界书、预设、构建配置等实际改动和发布记录，上述 `git add` 示例不是完整文件清单。推送后核实远端角色卡提交、前端 tag 与发布记录一致，核对分发 PNG 的 SHA-256 与已测试文件相同。若验收后又修改源码、指针或 PNG，重新执行受影响的构建与验收步骤。

### 三库远端核对

分别在三个仓库运行 `git rev-parse HEAD` 和 `git ls-remote origin refs/heads/main`，确认发布提交已推送。前端另外核对 tag 的解引用 SHA。记录三个仓库的提交及路由插件部署、联调结果；仅复制路由配置 JSON 不等于发布了插件代码。

## 九、回滚原则

- 不删除或移动已经发布的前端历史 tag。
- 新版本异常时，把五个源文件中的指针恢复到上一个已验证 tag，重新手动生成 PNG。
- 不使用 `@master`、`@main` 或 `@latest` 代替固定 tag。

### 组件检测版本标识

开局检测页与状态栏设置共用 `src/shared/componentCheck.ts` 中的组件验证基线。发布时同步核对该基线、预设 `extensions.cultivation_card`（源文件为预设索引的扩展字段）与路由配置 `configMetadata` 中每本世界书的 `id/version`。当前本卡标识为 `bengexiuxian`，组件修订号采用日期式版本；它与交付文件的 Ver. 版本号、路由文件格式 version 分开维护。

路由插件从 0.19.6 起提供只读 `CultivationRuleRouter.getDiagnostics()` 接口，并在导入、导出及本地同步时保留本卡版本标识；导入无标识旧配置会清除对应旧标识。插件版本、配置格式顶层 `version`、每本世界书的 `configMetadata[世界书名].version` 是不同概念，不能互相替代。

发布时逐项适配：

- 酒馆助手、提示词模板、路由插件：核对已安装插件的 manifest 版本、运行接口及启用状态；基线是本卡验证过的最低版本，不代表在线最新版。
- MVU：只检查 `getMvuData`、`parseMessage` 是否为可调用接口，正常显示“运行接口就绪”。不把缺少版本号当作落后或未安装，也不宣称已验证 MVU 版本；缺失或未加载完毕时提示重新检测。
- 当前聊天预设：从正在使用的预设读取 `extensions.cultivation_card`，其中 `id: bengexiuxian`、`version` 必须随 bundle 保留。更改本地索引后必须重新打包，单纯修改 JSON 文件名不会写入检测版本。
- 本卡路由配置：根据当前角色绑定世界书匹配诊断接口中的配置，检查总开关、启用规则和每本世界书的版本标识。新增或改名世界书时同步维护元数据键。配置修订号只在配置实际改变时更新；未变时保持原标识并复用原交付文件。
- 测试正则只决定前端加载入口，不负责插件、MVU 或配置版本标识。检测到“未标注版本”并不等于规则未加载，应核对实际导入的数据，不能仅凭本地源文件有标识就认定酒馆已更新。

升级顺序：更新路由插件 → 刷新酒馆使新版导入逻辑生效 → 导入交付预设并选中 → 通过路由插件导入交付路由配置 → 打开检测页重新检测。更新插件不会自动补齐已导入配置的版本标识；先用旧插件导入、再更新插件的情况需要重新导入。无需开启实验性宏引擎，保持关闭。

验收覆盖开局组件页和状态栏“组件检测”页，以及模型模式、变量模式切换。确认四个模型头部互斥，切换不会改动酒馆实际 API 连接；主 API/额外 API 的预设与世界书开关联动。路由插件的模型输入框支持手输并保存，获取列表仅更新候选项、不覆盖当前输入。
